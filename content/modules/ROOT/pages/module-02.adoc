== How do layers interact

We know that `dnf` can clean up after itself and that containers are usually rebuilt and replaced, not updated in place.
We can add a line to remove the cache, that should solve our problem.

First, let's change into the working directory from here on and use the more conventional format for builds
[source,bash,role=execute]
----
cd ~/my-container
----

Edit your `Containerfile` to add a new `RUN` line that removes all the working files for `dnf`.
[source,bash,role=execute]
----
vi Containerfile
----

[source,dockerfile]
----
FROM registry.access.redhat.com/ubi10/ubi
RUN dnf -y install httpd
RUN dnf clean all # <1>
EXPOSE 80
CMD ["/usr/sbin/httpd","-DFOREGROUND"]
----
<1> Added below the install — watch what happens.

Now rebuild the image, we can drop the explicit name of the file and use `.` as our context.
You will see this format very often in other examples that presume you are working in the context directory.

[source,bash,role=execute]
----
podman build -t my-webserver .
----

== The fix 

Let's look at the history once more to see the commands and layers.
[source,bash,role=execute]
----
podman history my-webserver
----

[source,text]
----
ID            CREATED         CREATED BY                                     SIZE        COMMENT
46c548924dc4  50 seconds ago  /bin/sh -c #(nop) CMD ["/usr/sbin/httpd","...  0B          
<missing>     50 seconds ago  /bin/sh -c #(nop) EXPOSE 80                    0B          
<missing>     50 seconds ago  /bin/sh -c dnf clean all                       95.7kB      
41270dafc48b  6 minutes ago   /bin/sh -c dnf -y install httpd                29.7MB      FROM registry.access.redhat.com/ubi10/ubi:latest
----

Well it says there's a difference of only about a hundred kilobytes, but notice how each `dnf` command is a separate layer? 
The removal of the cache files only happened in the layer *above* the install.
The files themselves still exist in the *original* install layer, from the cache.
Later layers can *hide* files from earlier layers in the final container, but they can't actually *remove* them.
All of the commands to effect a layer have to be in the same instruction in the `Containerfile`.

You'll see lines like this one in examples, where multiple commands are joined by `&&`.
[source,dockerfile]
----
RUN dnf -y install httpd && dnf clean all
----

If you look back at the `history` output, there's the key for why using a shell logical AND works.
A `RUN` instruction passes whatever is on the line into `/bin/sh -c` to be executed.
So shell syntax like `&&` to join multiple commands and `\` to continue lines for readability are common.

However, `podman` and `docker` support a better way to run more commands in readable ways, `heredoc` syntax.

Just like in shell syntax `<<` signals the start, and `EOF` is the delimiter that defines the script block.
We can add all sorts of useful things, not just our two `dnf` commands but also we can make sure RUN dnf clean all that an error in the `heredoc` will cause the step to fail and not give us a successful build of a broken image.

[source,bash,role=execute]
----
vi Containerfile
----

Replace the two `RUN` commands with the block below:
[source,dockerfile]
----
RUN <<EOF
set -e
dnf -y install httpd
dnf clean all
echo "Apache installed and cache clean"
EOF
----
Go ahead and rebuild the image.
[source,bash,role=execute]
----
podman build -t my-webserver .
----

Notice the build didn't use the cached install layer.
This is something to keep in mind as you design your `Containerfiles`.

So did putting both commands in one layer change the size?

[source,bash,role=execute]
----
podman images my-webserver
----

[source,text]
----
REPOSITORY              TAG         IMAGE ID      CREATED             SIZE
localhost/my-webserver  latest      740e05b7d4e1  About a minute ago  249 MB
----

Barely, and that's the point worth understanding here. There wasn't much cache to reclaim because the UBI base only pulls from a few small repositories. But because the cleanup ran in the *same* layer as the install, whatever cache existed never became part of the committed image. With a larger install or bigger repositories attached, that same technique can save hundreds of megabytes.
